# operations — 日常运维契约

**何时读我**：需要安排每日调度、历史回放、并发控制、峰值刷新或资产备份时。

## 每日顺序

1. **收盘后扫描**：`dragon-quant scan`（写库并触网；盘中扫描会因缺少收盘信息而失真，CLI 也会拦截）。
2. **盘后复盘**：`dragon-quant prep`，当日运行必须在 **16:40** 之后；`--force` 不绕过该门禁。
3. **次日竞价**：`dragon-quant auction`，当日 **09:25** 之后才可用；它默认读取严格 T-1 的复盘快照。
4. **买入信号**：`dragon-quant buy`，交易时段运行；需要对写信号表做确认。
5. **卖出信号**：`dragon-quant sell`，T+1 之后每个交易日至少运行一次。

## 峰值新鲜度

- 移动止盈、保本、首日窗口都依赖持仓峰值。每个交易日至少运行一次 `buy` **或** `sell`，二者都会刷新既有持仓的**峰值**。
- 如果连续几个交易日没有运行，峰值可能是旧的；此时不要断言“还没触发移动止盈”。
- 峰值是持仓期最高浮盈，不是当前收益；解释时不要混用。

## 历史回放

- `buy`/`sell` 历史日期必须同时给 `--date` 与 `--at`；只给其一会被拒绝。
- 实时当日回放截至当前已完成的 5 分钟 K；历史回放截至 `--at` 指定的时点。
- 回放会写信号表；同一状态重复运行是幂等的，输出会标注“未落库”。
- `--force` 只放宽午休/收盘时段，不解除交易日与 09:30 前限制，也不伪造收盘成交。
- 历史日期绝不使用今天的实时报价；日K兜底时成交价是保守近似。

## 并发

- `prep` 不与 `scan`/`rebuild` 并发运行；镜像双写是锁外 best-effort，错开可以避免缺日误判。
- `assets push`/`pull` 之间有进程锁；第二个进程会失败退出，不要强行并发。
- `buy`/`sell` 不要同时运行；它们都会写信号表，可能相互覆盖状态。
- 开启镜像后，T 日 `prep` 前建议先 `assets backfill-dragons --dry-run` 做只读体检。

## 数据耐久与备份

- `prep`/`auction` 产出后按需执行 `assets push`；推送前先 `assets push --dry-run`，确认范围与分区。
- `assets status` 看差异，`assets verify` 做定性校验，`--deep` 才下载内容。
- 恢复优先隔离目录 `assets pull --target-dir`；**禁止在主库执行 `assets pull --force`**。
- 就地恢复后如需收敛 dragons 镜像，用 `assets backfill-dragons --prune`（会删镜像孤儿行，属 T2）。
- 云端只是异地备份，本地是权威副本；`dragon.db` 不在资产同步范围内。

## 回放与幂等

- 同一 `--date`/`--at` 重复回放应得到一致决策；输出若提示“未落库”，通常是信号状态已变化或幂等命中。
- 不要用手工 SQL 改业务表来“修正”回放结果；状态不一致时先只读核对。
- 历史缺口（尤其是当日才可采的资产）不可再生，不要在事后假装补采成功。
